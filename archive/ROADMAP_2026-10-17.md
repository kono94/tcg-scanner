# TCG Scanner roadmap

Updated: 2026-10-17. The browser scanner pilot runs end to end (capture → corner detection → retrieval → review) on desktop Chrome with a test video. The work now is device verification, calibration on independent real captures, and a real-scene detector benchmark. No manual dataset creation is required. The [original audit](../docs/REPO_AUDIT_2026-10-15.md) records the earlier repository state.

## Product contract

Open a URL on a phone, wait for a steady scene or tap capture, then detect and recognize the actual cards in one immutable image. Review independent per-card results with a clean overlay, retry uncertain cards, and save physical copies once. Continuous tracking is optional later work.

Card count is variable, including zero and more than nine. Nine-card binder pages are a required benchmark slice, never a fixed input, required grid, or maximum. Enrollment adds reference images/metadata without expanding a classifier head; cross-game accuracy must be measured separately.

Follow the [capture policy](../docs/CAPTURE_CYCLE.md), [overlay specification](../docs/SCANNER_UX.md), [data contract](../docs/DATA_COLLECTION.md), and [recognition design](../docs/RECOGNITION_DESIGN.md). The legacy Python classifier remains a historical baseline.

## Implemented and executed

- `scripts/generate_synthetic_cards.py`: seeded composition of existing card fronts onto procedural binder, desk and plain backgrounds. Includes rotation, perspective, glare, illumination, blur, noise and JPEG effects. Exact renderer corners/identities are retained separately from derived minimum-area OBB rectangles.
- The local bootstrap contains **200 scenes, 1,321 instances, 160 training / 40 validation scenes**, with counts from **0 to 14**, including duplicate physical copies. Source identities and exact image hashes are disjoint across these splits. Near-duplicate appearances and renderer style are not independently held out.
- The generator creates YOLO labels, exact geometry annotations, canonical recognition query crops, source/preprocessing manifests and a preview. Optional replay has clean video pixels and separate per-frame labels; the generated example is **16 seconds / 160 frames**, with synthetic movement and steady holds.
- `training/card_detector/train_obb.py`: working YOLOv8 OBB training, including download-free random initialization. The smoke run and **20-epoch CPU bootstrap completed**, with zero corrupt labels. Best-checkpoint validation on 40 synthetic scenes / 269 instances reports precision **0.979**, recall **0.948**, mAP50 **0.991**, mAP50–95 **0.776**. These are detector metrics on the same generator domain, not recognition accuracy or real-camera results. Artifacts live under `runs/card_detector/obb/synthetic-bootstrap/`.
- `training/card_recognizer/canonical.py`: shared perspective canonicalization, whole-card aspect fit/padding and exact RGB/channel normalization, with a versioned contract hash.
- `scripts/prepare_card_gallery.py`: prepared **1,399 canonical reference crops** with identity/source/artifact hashes. This is image preparation, not a neural embedding index. Synthetic query crops use the same preprocessing contract.
- `scripts/build_embedding_gallery.py` / `retrieval.py`: built a **1,431-reference mixed pilot cosine index** from 1,399 One Piece and 32 acquired English Pokémon references using the same frozen 960-D MobileNet pooled features. No random projection or per-card classifier head is used. This is a baseline, not a generic-card accuracy result.
- Frozen MobileNet retrieval on **1,321 renderer-true-corner queries** reached Recall@1 **24.9%**, @5 **38.2%**, @20 **53.8%**. These queries derive from gallery source images; predicted detector crops and independent real captures are not included. The result is too weak to select this encoder for deployment. Preserve it as a reproducible comparison for stronger frozen descriptors.
- A **frozen DINOv2-small** comparison on the exact same 1,321 queries / 1,431-reference gallery improved Recall@1/5/20 to **37.4% / 48.3% / 61.1%**, without card-specific training. Maximum scoring across 0°/180° query views reduced top-1 to 35.8%. These historical synthetic stress-set results are insufficient for deployment. Frozen-DINO comparisons are stopped; proceed to pretrained-backbone retrieval fine tuning with the corrected data.

## 1. Complete the simple OBB-to-crop baseline

OBB had not failed in this repository: it had not been implemented or tested. The new trainer proves the format and training path work. Start with that implementation rather than introducing a separate corner network immediately.

- Inspect predicted OBBs on generated validation scenes and replay, including empty scenes, single cards, binder pages and more than nine cards. Measure missed cards, false/duplicate detections and count accuracy.
- Map predictions back to original source pixels and extract rotation-aligned full-card crops. Resolve the 180-degree orientation ambiguity explicitly; rectangle point order alone does not establish upright artwork.
- Compare predicted OBB crops with renderer-known perspective crops. Measure downstream retrieval differences before deciding whether perspective/corner refinement is needed.
- Scale scene diversity and detector input size where failures justify it. Generate additional deterministic seeds, varied pocket layouts/backgrounds and difficult small-card/glare examples automatically. Keep recipe, source and model hashes with results.

**Exit:** one command processes a still/replay with actual predicted boxes and inspectable source crops. OBB remains a rotated rectangle; exact synthetic quads remain available for diagnostics and future corner supervision.

## 2. Similarity recognition, with an optional OCR fast pass

Similarity search handles normal camera crops. A short OCR pass may resolve an exceptionally clear printed code cheaply; it is an optional shortcut, with quality/time gates to calibrate. OCR failure must not delay or block visual retrieval. The existing OCR-first offline proposal script records earlier experiments; it does not prescribe the production scheduler.

- After localization/rectification and quality assessment, encode usable crops and perform cosine search. Only exceptionally clear crops enter the optional OCR shortcut; expensive OCR retries belong to selective verification or offline experiments. Detect text regions across the card when OCR is attempted, without assuming a universal ID corner. PaddleOCR is a candidate backend to compare with Tesseract.
- One Piece base codes can be shared across alternate art; Pokémon collector numbers recur across sets; Yu-Gi-Oh! passcodes identify an underlying card rather than every printing. Require set/language/variant evidence appropriate to the requested identity. Never autocomplete unreadable characters, force the nearest catalog code, or treat a plausible string as a verified label.
- Direct code lookup can produce an OCR/catalog candidate when evidence is sufficient. Similarity is the main path and disambiguates shared-code artwork; OCR can also verify a shortlist selectively. Preserve observed text, regions, confidence, source frame and the reason for resolution or quarantine. No manual labeling by the user is required.

- Use one frozen encoder and the same versioned query/gallery tensor contract. Start with normalized descriptors and exact matrix cosine search at this catalog size; a vector database service is unnecessary initially.
- Record encoder/preprocessing/catalog hashes, identity mapping, vector dimension/type and normalization. Reject incompatible query/index artifacts. Adding references should rebuild/extend the compatible index without classifier-head retraining.
- Preserve the executed frozen baselines; do not repeat frozen-DINO experiments. Next compare card-specific fine tuning of a pretrained backbone with a retrieval objective. Keep backbone, projection/pooling and loss as separate configuration choices. Preserve variants such as `_p1`; score the next distinct identity rather than another reference of the same identity.
- Test pretrained localization and retrieval separately before adding card training: GroundingDINO proposes text-prompted boxes; DINOv2-style descriptors support gallery search. GroundingDINO boxes are axis-aligned proposals, not exact card IDs, physical-card proof or perspective corners. Larger pretrained models can serve as offline teachers while phone latency is measured separately.
- Compare true-corner versus predicted-OBB queries, clean versus degraded images, and training-held-out identities enrolled only in the gallery. Report Recall@1/5/20, wrong variants, quality failures, accepted precision/coverage and not-enrolled false accepts.
- Establish unknown/retry outcomes and calibrated thresholds. A nearest neighbor always exists; its existence does not prove the card is enrolled or correctly recognized. Synthetic thresholds are provisional until validated on independent camera queries.

**Exit:** an end-to-end synthetic scene → detector → crops → exact-ID shortlist report, with errors separated into localization, crop/orientation, image quality and descriptor/gallery failures.

## 3. Automate data expansion and strengthen only measured weaknesses

Run this alongside the baseline; missing real-camera data does not block implementation or synthetic training.

- Reuse existing official-reference ingestion and add source adapters for other games with explicit provenance, namespaces and variant mappings. Audit corrupt files, exact/near duplicates and missing metadata automatically.
- Address SAMPLE watermark mismatch before treating the reference set as clean. Prefer genuine scans; test AI-restored candidates separately on independent queries. See [image-source findings](../docs/IMAGE_SOURCES.md) for the completed example and concrete Roboflow/API/marketplace candidates.
- Mine reusable tournament/binder/deck-profile videos for real views. The [video-mining command](../docs/VIDEO_MINING.md) selects diverse candidates with timestamps/source groups and now enforces source resolution. Short native-4K collection/binder/pack excerpts have been downloaded and mined; tournament VODs remain discovery candidates. Improve physical-card geometry using the new real diagnostics/teacher proposals before promoting crops to exact-label training.
- Require verified **1440p or higher**, preferably **2160p/4K**, for newly accepted footage. Inspect available format dimensions rather than trusting titles; gate individual crops on actual source pixels and legibility too. Luna source searches cover One Piece/Pokémon binder tours and openings, with Yu-Gi-Oh! as a transfer slice. A 1080p inspection excerpt is retained solely as a failed-quality example.
- Expand procedural backgrounds and rendering recipes; optional generated background assets can add variety. Keep card fronts and corner labels controlled by geometric composition. An LLM does not need to guess corners the renderer already knows.
- Use stronger vision models/LLMs to propose real-image detections, identities and difficult cases. Store teacher identity/version, confidence and agreement checks; pseudo-labels remain proposals, not independent ground truth. Keep acquired raw images/video separate from prediction overlays.
- Add independent real-domain calibration/testing as sources become available, split by capture/session before crops or augmentation. Existing ten `manual_eval` images duplicate training references and remain fixtures. The old 72-second `resources/processed/inference_example.mp4` contains burned-in predictions and cannot supply accuracy ground truth.
- If true-corner retrieval succeeds but OBB crops fail, test corner refinement/keypoints using existing synthetic corner supervision first. If both fail, improve encoder, gallery or available image detail. OBB is the initial implementation, not a promise that perspective never matters.
- Fine-tune a pretrained visual encoder using ArcFace or a separately measured supervised-contrastive recipe; do not make from-scratch backbone training the default. Start with controlled known-ID reference-derived views, add automatically corroborated real pairs, and keep unresolved video crops unlabeled. Mine hard negatives among similar art/variants. Rebuild the gallery after training or distillation, and test held-out identities/capture sources.

**Exit:** improvements beat a fixed baseline on declared data domains. Publish synthetic results separately from independent real-domain results; real capture evaluation is required for real-world accuracy claims.

## 4. Browser capture cycle and clean overlay

Status: implemented as a pilot (see above) and verified only on desktop Chrome. The remaining items are the device checks, live price ranges/coverage beyond the bundled snapshot, and the closer single-card investigation flow.

- HTTPS camera → stability dwell/countdown → one immutable capture → detection → bounded per-card recognition → review. Provide manual capture and configurable repeat cooldown. Keep only one active batch; movement resets capture eligibility and page changes invalidate stale results.
- Thin white outlines, restrained white capture sweep, actual per-card queued/recognizing/ready/attention states, and compact page progress. Show selected-card details without covering every card face. A wait animation reflects pending work and stops on completion/failure.
- All boxes/results refer to the displayed snapshot. Repeat scans replace candidate observations; saving is idempotent per physical instance. Identical card IDs in different pockets remain separate copies.
- Pin compatible ONNX/runtime/model/index assets. Keep inference in a worker, test WebGPU and WASM fallback, and verify outputs/rankings against Python. Measure actual camera resolution and source pixels per card.
- Add preferred card language separately from interface language and currency. When language is unresolved, show an explicit assumed-language estimate; keep plausible alternatives and evidence separate. Details/review always expose the supported versions range or unknown value, price coverage and assumptions. Use compact `Check variant` cues for materially valuable compatible alternatives and a closer single-card investigation flow that preserves the original physical instance. Implement family mappings, price-service range queries and coverage/quote provenance before showing these as live values. See [match and value policy](../docs/MATCH_AND_VALUE_POLICY.md).
- Test physical iPhone/Safari and Android/Chrome: load time, first/settled result latency, memory, sustained use, background/resume and permission recovery. Prices stay behind a separate service.

**Exit:** a shareable URL runs actual inference on both phones with variable card counts, truthful states, bounded work and no duplicate accumulation.

## 5. Expand games and deployment quality

Enroll a second-game slice with mixed-game scenes, confusing variants and not-enrolled examples. Measure held-out identity/game performance separately. Enrollment makes a card searchable; encoder generalization and visible detail determine recognition quality. Visually indistinguishable printings require an ambiguity result or additional evidence.

Provisional product targets remain: at least 99% accepted exact-ID precision with at least 70% coverage for supported readable queries, at most 1% unknown false accepts, and no silent loss of instances above nine. These are goals, not current measurements. Report raw counts, uncertainty, complete-scene success and latency by actual count/layout. Initial phone goals are first confirmed result within one second and nine readable cards settled within five seconds after capture; revise from device evidence.
