# Cross-game recognition and Yu-Gi-Oh! data research

Status: desk research, 2026-10-15. This document proposes an evaluation path; it does not report a cross-game card-recognition result. Existing recognition-design and audit limits still apply: the repository has a One Piece corpus, no validated retrieval embedding, and no independent camera benchmark.

## Can one encoder cover several games?

One shared encoder and retrieval pipeline is a sound architecture to test. Enrollment lets each game contribute reference images and metadata without adding a classifier output for every new card. A pretrained visual model can provide useful off-the-shelf retrieval features: Meta's DINOv2 model card reports nearest-neighbor retrieval results on Oxford-H, plus broad visual tasks. The paper/model card do not establish exact card printing recognition, binder-photo robustness, or cross-game performance. [DINOv2 model card](https://github.com/facebookresearch/dinov2/blob/main/MODEL_CARD.md) [DINOv2 paper](https://arxiv.org/abs/2304.07193)

The visual task is unusually fine grained. A generic embedding may retrieve the same character/artwork or card family while missing a set, foil, language, edition, or alternate-art distinction. Yu-Gi-Oh! gives an especially clear example: the eight-digit passcode identifies the underlying card, while one card can have many `card_sets` entries with different set codes and rarities. An image can therefore match the card identity but still fail to prove which physical printing is present. The latest product direction uses similarity as the normal recognition path, with bounded OCR as a fast pass only on exceptionally clear crops or selective shortlist verification. Parse only observed ID-like strings and validate against catalog entries; never invent or autocomplete a code. If evidence remains insufficient, return unresolved. Neither OCR nor image retrieval has been measured on these Yu-Gi-Oh! videos.

Accordingly, the practical hypothesis is one common feature extractor and search service, with game-specific catalog adapters and verification rules. Start with frozen pretrained features and the present One Piece setup as baselines, then compare a shared fine-tuned encoder to game-specific adapters or fine-tuning. Split evaluation by physical copy/session and hold Yu-Gi-Oh! identities out of encoder training while enrolling their catalog references at query time. Report top-k retrieval, exact-printing resolution, unknown false accepts, coverage, and latency separately by game. This follows the repo's retrieval design; it is not a result already demonstrated here.

Sports cards should remain out of the first cross-game claim. Their catalog identity can depend on player, year, set, parallel, serial numbering, and sometimes autograph or memorabilia attributes. That expands both the visual distinctions and metadata model. Magic is a more straightforward next catalog adapter than sports, but its set symbol and card finish / treatment variants still require evaluation. The TCGplayer set-identification guide itself describes game-specific visual cues and exceptions. [TCGplayer set-identification guide](https://help.tcgplayer.com/hc/en-us/articles/360025635234-How-do-I-identify-card-sets)

## Catalog identity and automatic labeling

Pokémon has a relatively direct printed key for many modern cards: set plus collector number, commonly shown as `XXX/YYY`. The number is useful but is not guaranteed to be unique across language/region or all special printings. Catalogs should retain set code, region/language, collector number, card variant/treatment, and source identifier rather than flattening those fields into one guessed label. The Pokémon TCG API docs currently state, “The Pokémon TCG API is deprecated. New account registrations are no longer available. Existing API keys will continue to function through March 1, 2027. Please migrate your application to Scrydex.” This warning appears at the top of its current set endpoint documentation; the docs also describe Version 1's separate 2021 deprecation. Therefore, its current warning is directly supported and it should be treated as a migration-limited source, not assumed to be a durable new production dependency. [Current Pokémon TCG API set endpoint docs](https://docs.pokemontcg.io/api-reference/sets/get-set/) [API docs overview](https://docs.pokemontcg.io/)

For Yu-Gi-Oh!, use two levels of identity:

- **Underlying card:** the eight-digit passcode / catalog card ID. YGOPRODeck documents `id` as the passcode and exposes card images (including alternate-art images) under that identity.
- **Printing:** `card_sets` entries include set name, set code, rarity, and price. The printed set code can narrow a physical printing. Preserve language/region and first-edition, limited, or unlimited distinctions when the catalog supports them; the code alone may not resolve all of these.

YGOPRODeck's API is a practical candidate catalog source, with local caching required by its guide and current rate limits. The API is community-maintained, not a Konami identity authority. TCGplayer's guide describes Yu-Gi-Oh! card numbers as encoding set, region, and set position, and notes old-card exceptions. Recommended label flow: visual retrieval proposes a shortlist; selective OCR/catalog evidence narrows identity when legible. An exceptionally clear crop may take a bounded OCR shortcut. Store OCR text/confidence, source region/timecode, catalog response/version and visual candidates. Never fill in or infer missing characters in a code. Conflicts or weak evidence become `unresolved` or `quarantined` automatically and are excluded from verified ground truth; user work is not required. All automatic proposals remain unverified until independently validated. [YGOPRODeck API guide](https://ygoprodeck.com/api-guide/) [TCGplayer Yu-Gi-Oh! set-number guidance](https://help.tcgplayer.com/hc/en-us/articles/360025635234-How-do-I-identify-card-sets)

### Binder tours and pack openings as candidate footage

The candidate list in [`resources/benchmarks/yugioh_video_candidates.json`](../resources/benchmarks/yugioh_video_candidates.json) contains two binder/collection videos and three pack-opening videos. Their source resolutions have not been verified. Because usable card-crop detail matters, accept only videos with verified source resolution of at least 1440p, preferably 2160p; candidates marked `unknown` are not eligible inputs until actual resolution metadata is checked. A title or thumbnail claim is not resolution evidence. No Yu-Gi-Oh! frames have been downloaded, inspected, annotated or scored in this research pass. For eligible inputs, similarity supplies the usual shortlist; OCR is an optional clear-crop shortcut or verifier. Weak/conflicting cases become unresolved/quarantined automatically, not a manual screening queue. All automatic proposals remain unverified until independently validated and must not be represented as ground truth.

For future automated labels, combine visual candidates with catalog constraints and any exact observed OCR tokens. Captions, narration, pack/set context and neighboring frames are secondary constraints; they do not substitute for absent characters in a card code. Never guess missing code characters. Keep source/timecode and confidence, collapse repeated frames of one physical card into one event, and allow unknowns. A pack-opening sequence can constrain possible cards only if product and collation are known; it must not force an exact label. Low evidence leads to unresolved/quarantined status without user screening.

## Recommendation

Keep the core as a shared retrieval system evaluated first on One Piece and Pokémon, then use held-out Yu-Gi-Oh! as a transfer gate before claiming three-game support. Add Yu-Gi-Oh! once that gate has a catalog adapter, independent binder/pack query captures, exact-card versus exact-printing labels, and unknown rejection. Do not add sports cards or Magic to the first encoder claim; establish the two-game protocol and Yu-Gi-Oh! transfer behavior first. In parallel, preserve Magic as a low-cost metadata adapter candidate for a later catalog expansion. This makes the architecture generic while keeping accuracy claims tied to measured games and printing granularity.
